## 1. 结论

Candidate B 暂不通过。

当前 `48 / 80 / 14` 的战斗压力已经接近目标区间，但实机暴露出两个耦合问题：

1. **回合反馈不可读**：技能结果与敌方行动衔接过快，玩家来不及看清“我刚刚做了什么、恢复了多少、随后又受到多少伤害”。
2. **低质量回复主观上仍显得过强**：`failed = 0.40` 时，回潮仍为 `4伤害 + 9回复`。即使敌方随后造成约 `14` 伤害，净结果约为 `-5 HP`，玩家首先看到的是明显回血，容易形成“答错也得到不少奖励”的感觉。

因此当前不能仅凭 HP 曲线判定 Candidate B 通过，也不应继续单纯提高敌方伤害。

## 2. Candidate B 已证明的内容

工程与确定性曲线成立：

- Phase B：玩家 `48` / 敌人 `80` / 敌伤 `14`；
- 全 independent：约第 5 回合胜，约 `23 HP`；
- 一次 failed 后恢复：约第 6 回合胜，约 `10 HP`；
- 连续两次 failed 的代表路径会在击杀前战败；
- 持续 failed 无获胜路径；
- 回潮 independent 仍保留 `22` 回复的救场价值；
- 默认 Phase A debug `48 / 60 / 8` 未被破坏。

这些说明**压力参数本身已接近可用区间**，但还不能证明玩家能正确感知代价。

## 3. 当前优先级裁决

下一轮不再优先加敌伤。

先处理两件事：

### A. 采用成熟顺序回合制反馈

不自造复杂战斗系统，只采用成熟回合制/JRPG 的标准表达：

`选择技能 → 玩家技能结算 → 看清数值与 HP 变化 → 敌方行动提示 → 敌方伤害结算 → 看清数值与 HP 变化 → 再开放技能选择`

核心规则：

- 结算期间锁定输入；
- 玩家技能结果与敌方结果分开呈现；
- 回复使用绿色 `+数值`；
- 受伤使用红色 `-数值`；
- HP 条跟随结果平滑变化；
- 下一次技能选择必须等当前双方行动反馈稳定后才开放；
- 不要求玩家靠反应速度追动画。

产品冻结的是**阶段顺序与可读性**，不是永久锁死某个毫秒值。下一候选原型可以以每个关键结果约 `1.2s` 的可读停留作为测试起点，后续实机再微调。

### B. 低质量倍率候选改为 25% / 25%

下一候选只作为 Phase B 独立原型测试：

- independent：`1.00`，不变；
- supported：`0.70`，不变；
- failed：候选 `0.25`；
- no-call：候选 `0.25`。

`failed` 与 `no-call` 必须一起变，禁止只削 failed。

对应：

- 回潮 failed：`10 × .25 → 3伤害`，`22 × .25 → 6回复`；
- 水音 failed：`18 × .25 → 5伤害`，`20% × .25 → 5%削弱`。

在敌伤 `14` 下，低质量回潮的“回血后再挨打”净代价会更明显，同时 independent 回潮仍保持 `10伤害 + 22回复`。

## 4. 为什么不继续提高敌伤

若只继续把敌伤从 14 往上加：

- 可以让数学惩罚更大；
- 但仍解决不了玩家看不清“先回复、再受伤”的问题；
- 还会快速把一次失误推向不可挽回，违背零基础用户“一次错还能救”的原则。

所以顺序必须是：

> **先让玩家看懂代价，再判断代价够不够重。**
