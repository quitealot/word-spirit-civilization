# 《词灵》剧情内容交付接口（K3）

状态：稳定接口 v1，供 K3 直接交付剧情内容；字段变更需先经 Sol Review。

## 先看这一条

从本接口建立起，K3拥有《词灵》正式剧情、人物对白和叙事动作文本的最终内容权。

仓库当前已经能运行的Opening、EP01–EP04，以及EP05–EP10中的临时文本，都只是：

`TEMPORARY_CONTENT_PENDING_K3`

它们用于验证流程、UI、存档和战斗衔接，不代表正式剧本，也不限制K3的文学表达。K3正式稿通过同一个`sceneId`交付后，程序只替换内容层，不应要求重写玩法逻辑。

## 交付目标

K3只需要提交“场景内容数据”，不需要写React、TypeScript、状态机或任何程序逻辑。可以先用下方的YAML样式文本、Markdown表格或JSON交付；Codex负责把内容校验并接入内容层。

每个场景必须有稳定的`sceneId`。已有场景优先沿用项目提供的ID；如果确实需要新场景，先提出新的ID和用途，不要自行改变已有玩法入口。

推荐的交付外壳如下：

```yaml
sceneId: ep01.resonance
status: K3_DRAFT
beats:
  - id: ep01.resonance.b01
    type: dialogue
    speaker: 阿洛
    text: "这里放阿洛的正式对白。"
  - id: ep01.resonance.b02
    type: action
    actor: 芽语
    text: "这里放可被画面表现的动作。"
    presentation: light_fx
```

`status`只用于内容流转，建议使用：

- `K3_DRAFT`：K3已提交，等待Sol整体一致性Review；
- `REVISE`：Review提出修改，仍由K3改内容；
- `APPROVED_FOR_INTEGRATION`：Sol通过，可进入游戏；
- `INTEGRATED`：已接入并完成程序回归；
- `TEMPORARY_CONTENT_PENDING_K3`：当前旧文本或占位文本，禁止视为正式稿。

## 一集可以使用的叙事积木

积木只描述玩家看到或读到的内容。它们不直接改变探索力、战斗、词汇、存档或解锁。

### 1. dialogue：人物对白

必填：

- `id`：本段唯一ID；
- `type: dialogue`；
- `speaker`：界面显示的人物名；
- `text`：对白正文。

可写自然口吻、停顿、反问、误解和人物关系。需要换行时在正文中明确标注，避免依赖程序猜测。

### 2. narration：叙事说明

必填：

- `id`；
- `type: narration`；
- `text`。

用于环境、视线、声音、天气、玩家当下可观察到的变化。叙事说明应只写玩家此刻能够感知的内容，不替玩家宣布尚未发生的真相。

### 3. action：人物或语灵的叙事动作

必填：

- `id`；
- `type: action`；
- `text`。

可选：

- `actor`：动作主体；
- `presentation`：`portrait`、`sfx`、`light_fx`或`scene`之一，用于提示已有表现方式。

动作应当是可用现有立绘、背景、轻特效或声音表现的叙事动作。它可以表现观察、后退、停顿、靠近、回头等，不会自动增加技能或系统效果。

### 4. choice：玩家选项文字

必填：

- `id`；
- `type: choice`；
- `choices`：至少两个选项，每项包含`id`和`text`。

选项文字由K3负责，选项的实际结果由玩法配置负责。若某个选项只是不同口吻、不会改变流程，也请注明“表现分支，不改状态”。如果选项需要改变关系、获得物品、开启路线或改变战斗，必须在交付备注中提出给Sol/Codex Review，不能把效果藏在对白里。

### 5. interaction：固定互动提示和结果文字

用于已经由玩法配置定义好的低成本互动，例如“绕开翘起木板，把行李放到墙边”或“停下看一眼湿脚印”。

必填：

- `id`；
- `type: interaction`；
- `interactionId`：程序已有或待确认的互动ID；
- `prompt`：按钮/提示文字；
- `resultText`：玩家完成观察后看到的短文本。

互动是否可用、是否暂停、是否推进场景由程序处理。K3可以决定这一刻玩家看到什么和人物如何反应，但不能借此新增道具、奖励、英语题、自由移动或隐藏分支。

## 一个很短的示例

下面只是格式示例，不是《词灵》正式内容，也不冻结任何对白：

```yaml
sceneId: example.harbor-arrival
status: K3_DRAFT
beats:
  - id: example.harbor-arrival.b01
    type: narration
    text: "雾贴着木栏慢慢散开，码头还没有完全醒来。"
  - id: example.harbor-arrival.b02
    type: dialogue
    speaker: 阿洛
    text: "行李先放这边，别挡着送货的路。"
  - id: example.harbor-arrival.b03
    type: interaction
    interactionId: opening.luggage
    prompt: "绕开木板，把行李放到墙边"
    resultText: "你把行李挪到墙边，给来往的人让出一条路。"
  - id: example.harbor-arrival.b04
    type: action
    actor: 阿洛
    text: "他抬手指了指雾里的屋檐。"
    presentation: scene
  - id: example.harbor-arrival.b05
    type: choice
    choices:
      - id: ask-who
        text: "你要带我去见谁？"
      - id: ask-work
        text: "今天先做什么？"
```

这里的对白、动作和按钮文字可以由K3自由改写；`opening.luggage`这个互动的实际流程仍由程序掌管。

## K3可以决定什么

K3可以决定：

- 人物在既定场景中的说话方式、语气、停顿和潜台词；
- 叙述顺序、可观察的环境细节和人物动作；
- 玩家选项的文字与表现分支；
- NPC对玩家、初伴、绒岚、野生语灵和事件的具体反应；
- 在已提供的表现预算内，某个动作使用立绘、声音、轻特效还是场景提示；
- 正式场景中的文学节奏、生活化细节和情感落点。

如果K3认为需要新人物、新场景、新互动或新资产，可以在场景末尾增加“内容提案”段落说明原因；它不会自动变成已批准的玩法或资产。

## K3不能单方面决定什么

以下由Sol/Codex的产品和玩法配置掌管，不能通过剧情文本偷偷改变：

- `sceneId`对应的进入条件、探索力门槛、地图解锁和章节完成；
- 战斗开始/结束、敌人生命、技能效果、换位冷却、战败重试和奖励；
- L1/L2/L3题型、FSRS调度、Mastery、答题正确判定和学习数据；
- 伙伴获得、重复获得防护、队伍容量、经验、共鸣和升星；
- 道具、货币、图鉴、竞技入口、后端和存档字段；
- 需要新增美术、复杂动画、自由移动或新的系统能力；
- 玩家身份和已冻结事实：玩家只是刚到雾港做短期跑腿工作的普通新人，不是天选者、调查员、召唤者或拥有特殊权限的人；
- 绒岚的已冻结生物核心、三次目击顺序和禁止的教学工具能力；
- 旧路、无名碑、大失语、天空传说或守门人的最终真相。

K3可以写人物“看见了什么”“以为是什么”或“拒绝解释什么”，但不能在未经Review的文本里把悬念直接写成世界观答案。

## 固定事实与自由表达的边界

以下顺序和玩法接口是固定的，内容可以由K3重写：

`抵达雾港 → 阿洛接人 → 两次生活互动 → 认识岑婆 → 语灵站 → 观察三只初伴 → 三选一 → 共鸣 → 3个L1 → EP01后半段`

EP05–EP10当前只提供玩法骨架和占位场景。K3可以决定这些场景的正式对白、叙事动作和情绪节奏，但不应把占位内容误认为既定剧情答案。

对固定角色的动作描写尤其要遵守：绒岚是小型狸/貂型语灵，有三层柔软页片尾，警惕且观察性强，不喜欢被追；玩家停止靠近后，它才会主动缩短距离。禁止给它修书、补页、控文字、翻译、恢复单词或其他教学工具能力。

## 程序会处理什么

程序负责：

- 按`sceneId`加载场景，并按`beats`顺序展示；
- 显示说话人、立绘、背景、按钮、轻特效和可用的断点；
- 校验字段、ID重复、缺失文本和不支持的`presentation`；
- 处理选择按钮的流程结果、互动状态、地图、战斗、学习、FSRS、存档和埋点；
- 在K3正式稿替换临时稿后，保持相同玩法接口；
- 对需要Sol确认的新增内容标记Review，不把文本中的新效果自动解释成系统规则。

K3不需要写“进入下一集”“增加探索力”“开始战斗”“保存存档”等程序指令。若场景需要这些转场，只引用已分配的场景/互动/战斗ID，并在交付备注中说明意图。

## 交付前自检

提交每集内容前，请确认：

1. 每个场景和每个beat都有稳定、唯一的ID；
2. 每个对白都有明确`speaker`，每个动作都能看出主体；
3. 玩家选项只写玩家会看到的文字，不把奖励或状态写进选项定义；
4. 固定互动使用已有`interactionId`，没有暗中增加题目、道具或奖励；
5. 没有把临时占位文本当成正式设定；
6. 新设定、新资产和新玩法另列“内容提案”，等待Sol Review；
7. 正式稿的状态写为`K3_DRAFT`，不要直接写`APPROVED_FOR_INTEGRATION`。

这份接口限制的是交付格式，不限制K3的文学表达。最终对白、动作和叙事节奏由K3负责；Sol负责整体一致性Review，Codex负责把已通过的内容可靠接入游戏。
